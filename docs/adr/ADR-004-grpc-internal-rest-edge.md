# ADR-004 — gRPC внутри, REST на границе; контракты в `proto/` под buf

**Статус**: принято
**Дата**: 2026-06-11

## Контекст

Нужно зафиксировать протоколы: как клиент говорит с бэкендом (north-south) и как сервисы говорят между собой (east-west), и где живут контракты. Без единого решения контракты расползаются: рукописные REST-типы на фронте дрейфуют от бэкенда за месяц, межсервисные интерфейсы ломаются незаметно.

## Решение

**East-west — gRPC.** Все межсервисные вызовы (gateway → сервисы, realtime → Core, Core → Billing) — gRPC/protobuf: строгие контракты, кодогенерация, deadlines из коробки, дешёвые стриминг и metadata (trace context, Idempotency-Key).

**North-south — REST + WebSocket + WebRTC.** Клиент никогда не говорит по gRPC:

- REST (JSON) через API Gateway — для всего запрос-ответного;
- WebSocket к Realtime — события комнат, чат, Yjs-апдейты;
- WebRTC к LiveKit — медиа.

**Контракты — один модуль `proto/` в корне монорепы под buf:**

```
proto/trajectory/auth/v1/ · education/v1/ · billing/v1/ · events/v1/
```

- `buf lint` + `buf breaking` в CI — несовместимое изменение не мёржится;
- payload'ы событий JetStream — тоже protobuf (`events/v1`), один источник правды для sync и async контрактов;
- версионирование пакетов (`v1`) — эволюция через добавление полей и новых версий, не через ломку;
- Gateway публикует OpenAPI-спеку → генерация TypeScript-клиента фронтенда. Рукописных API-типов нет нигде.

## Альтернативы

- **REST между сервисами.** Отклонено: контракты на словах (OpenAPI пишется руками и врёт), нет deadlines/metadata из коробки, дороже сериализация.
- **gRPC-web до клиента.** Отклонено: усложняет браузерную сторону (прокси, ограничения стриминга), REST+OpenAPI даёт тот же типизированный клиент проще; WebSocket для realtime всё равно нужен отдельно.
- **GraphQL на границе.** Отклонено для MVP: продуктовые экраны хорошо ложатся на REST-ресурсы; federation/резолверы — лишний слой над шестью сервисами.
- **Контракты в репозиториях сервисов.** Отклонено: дубли и дрейф; монорепный `proto/` — единственный источник правды.

## Последствия

- (+) Запрос типизирован на всём пути: TS-клиент → OpenAPI → gateway → protobuf → сервис.
- (+) Ломающее изменение контракта видно в CI, а не в проде.
- (+) Идемпотентность и трассировка едут в gRPC metadata единообразно.
- (−) Двойное описание границы (REST ↔ gRPC-маппинг в gateway) — цена изоляции внутренних контрактов от публичных.
- (−) buf и кодогенерация — обязательная часть пайплайна с первого дня.
