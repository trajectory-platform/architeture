# ADR-002 — Синхронизация вайтборда: Go relay с персистентностью (Path A)

**Статус**: принято
**Дата**: 2026-06-11

## Контекст

Доска — совместно редактируемый документ на Yjs (CRDT). Нужен серверный компонент: рассылать апдейты участникам, хранить состояние, отдавать его при reconnect и холодном входе. Проблема: у Yjs **нет зрелой серверной реализации на Go** — эталонные серверы (y-websocket, Hocuspocus) живут в экосистеме Node/TypeScript, а бэкенд проекта — Go.

## Решение

**Path A: realtime-сервис на Go — «тупой» relay с персистентностью.** Сервер не интерпретирует Yjs-апдейты. Это корректно благодаря свойствам CRDT-апдейтов: они коммутативны, идемпотентны и самодостаточны — мерж выполняют клиенты, детерминированно и одинаково.

Обязанности сервера сводятся к трём:

1. **Append** — апдейт (opaque `bytea`) дописывается в per-room лог с монотонным `seq`;
2. **Broadcast** — рассылка остальным участникам (fan-out между инстансами — Redis Pub/Sub);
3. **Replay** — на reconnect/вход: последний снапшот + хвост лога (`snapshot + tail`); клиентский Yjs идемпотентно отбрасывает уже применённое.

Компакция (снапшот = слитое состояние документа):

- основная стратегия — **Node-сайдкар**: маленький воркер, по порогу выполняющий `Y.mergeUpdates(snapshot, tail)` и записывающий новый снапшот;
- упрощённая (допустима на раннем MVP) — периодический push `Y.encodeStateAsUpdate` клиентом преподавателя.

Снапшот — оптимизация чтения; корректность от него не зависит (полный replay лога эквивалентен).

Детали протокола: [05 — Realtime и вайтборд](../architecture/05-realtime-whiteboard.md).

## Альтернативы

- **Path B: Hocuspocus (Node/TypeScript) как выделенный sync-сервис.** Зрелый сервер Yjs из коробки: awareness, хуки персистентности, debounce. Минусы: второй язык в бэкенде (инструментамент, деплой, найм), вся realtime-логика комнат (presence, чат, авторизация) либо переезжает в Node, либо размазывается на два сервиса. Под жёсткий дедлайн выбрали бы его; здесь инженерная глубина — часть цели проекта.
- **Серверный CRDT-мерж на Go** (порты y-crdt/yrs через cgo или самописный). Отклонено: незрелые биндинги, высокий риск тонких багов конвергенции, и главное — серверный мерж не нужен, relay достаточен.
- **OT / lock-based синхронизация.** Отклонено: OT требует центрального арбитра и трансформаций под каждый тип операции; CRDT решает конфликт-резолюшн бесплатно и переживает офлайн-правки.

## Последствия

- (+) Весь realtime — один Go-сервис; сервер не может «неправильно смержить», т.к. не мержит.
- (+) Горизонтальное масштабирование и отказоустойчивость тривиальны: инстансы равнозначны, состояние — лог + Redis.
- (+) Лог апдейтов даёт бесплатный history/replay урока.
- (−) Node-сайдкар для компакции — маленький, но всё же не-Go компонент (изолирован: читает и пишет только лог, без внешнего API).
- (−) `snapshot + tail` шлёт надмножество нужного (сервер не умеет диффы по state vector) — переплата трафиком на reconnect; для документов размера «доска урока» приемлемо.
- (−) Сервер не валидирует содержимое доски (блоб опаковый) — авторизация только на уровне «кто в комнате».
