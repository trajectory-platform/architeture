# ADR-005: Архитектура и бизнес-правила Public API (API Gateway)

**Статус:** Принято (Accepted)
**Дата:** 2026-07-08

## 1. Контекст (Context)

В процессе проектирования единого OpenAPI контракта (`api.yaml`) для публичного шлюза (API Gateway) потребовалось определить строгие границы ответственности между клиентской частью (Web/App) и микросервисным бэкендом.

Система должна обслуживать две основные роли (Ученик и Преподаватель) и быть устойчивой к специфическим векторам атак: переполнению памяти (OOM), распределенным сбоям, микротранзакционному фроду (убытки на эквайринге), спаму в системе обмена сообщениями и разрушению сетки расписания. Требовалось зафиксировать единые правила по работе с деньгами, файлами, пагинацией и часовыми поясами до начала реализации внутренних gRPC-контрактов.

## 2. Решение (Decision)

Мы приняли следующие комплексные архитектурные и бизнес-правила:

### 2.1. Финансы и Биллинг (Billing Service)
* **Тип данных:** Все денежные значения в API передаются исключительно в минорных единицах (копейках) целочисленным типом (`integer`), чтобы исключить ошибки округления (float) на стороне клиента.
* **Бизнес-защита (Анти-фрод):** Установлен жесткий минимальный порог на пополнение баланса и стоимость урока — 500 рублей (50000 копеек). Это защищает систему от финансовых потерь на фиксированных комиссиях платежных провайдеров (например, ЮKassa).
* **Модель баланса:** Баланс отдается в агрегированном виде: `total` (фактический остаток в леджере), `held` (замороженные средства) и `available` (доступные средства).

### 2.2. Расписание и Бронирования (Core Education)
* **Динамические слоты (Infinite Calendar):** Свободные окна генерируются бэкендом "на лету" на основе базовых правил преподавателя (`availability_rules`) за вычетом уже подтвержденных броней. Фронтенд обязан запрашивать слоты строго по неделям (`start_date`, `end_date`).
* **Оптимизация сетки (Anti-Swiss-Cheese):** Для максимизации дохода репетиторов начало уроков разрешено только в `:00` и `:30` минут. При длительности урока 55 минут это обеспечивает плотную упаковку расписания без "мертвых" окон.
* **Логика бронирования:** Ученики могут создавать только регулярные занятия (подписки). Преподаватели могут назначать как регулярные, так и разовые уроки.
* **Часовые пояса:** Жестко используется стандарт IANA (например, `Europe/Moscow`). Правила расписания не могут переходить через полночь в рамках одной сущности.

### 2.3. Идемпотентность и Саги (Distributed Transactions)
* Бронирование урока запускает распределенную транзакцию (Saga) между Core и Billing сервисами.
* Для защиты от двойных списаний при ретраях сети, метод `POST /bookings` требует обязательной передачи уникального заголовка `Idempotency-Key` от фронтенда.

### 2.4. Безопасность и Авторизация (Auth Service)
* **Разделение токенов:** JWT Access-токен передается в заголовке `Bearer`, а Refresh-токен — строго в `httpOnly` cookie для защиты от XSS.
* **Защита от Enumeration-атак:** Ручки восстановления пароля возвращают `200 OK` независимо от наличия email в базе, чтобы скрыть пользовательскую базу от парсинга.
* **Изоляция ролей:** Регистрация администраторов через Public API закрыта. Ученикам на уровне контракта запрещено изменять поля преподавателя (возвращается `403 Forbidden`).

### 2.5. Файловое хранилище (MinIO / Uploads)
* **Direct Upload (Прямая загрузка):** API Gateway не проксирует медиафайлы. Клиент запрашивает временную ссылку (`Presigned URL`) и загружает файл напрямую в S3.
* **Защита хранилища:** Бэкенд ограничивает размер файла (до 5 МБ) и жестко валидирует разрешенные MIME-типы (изображения и PDF) на этапе генерации ссылки, защищая облако от переполнения и Stored XSS атак.

### 2.6. Чаты (Realtime Service)
* **Социальная изоляция (Анти-спам):** Публичное создание чатов с любым UUID запрещено (`403 Forbidden`). Переписка доступна только между пользователями, имеющими активную связь через подтвержденные бронирования (чат создается автоматически через события NATS).
* Во всех списках (история чатов, уроки, преподаватели) реализована обязательная пагинация с жестким лимитом (`maximum: 100`) для предотвращения OOM (Out Of Memory) на сервере.

## 3. Последствия (Consequences)

* **Положительные:**
* API Gateway полностью защищен от высоких нагрузок по памяти (работа с файлами делегирована).
* Финансовая модель устойчива, а преподаватели получают оптимально заполненное расписание без простоев.
* Исключены дублирующиеся финансовые транзакции благодаря идемпотентности.
* Платформа защищена от парсинга базы и рассылок спама.
* **Отрицательные:**
* Существенное усложнение логики на стороне фронтенда: разработчику придется реализовать двухэтапную загрузку файлов в S3, управлять генерацией `Idempotency-Key`, обрабатывать асинхронные статусы Саги (`PENDING` -> `CONFIRMED`) и строго форматировать даты/таймзоны при запросе расписания.
