# ADR-001 — Гранулярность микросервисов: пять сервисов, не больше

**Статус**: принято
**Дата**: 2026-06-11

## Контекст

Спецификация проекта требует микросервисной архитектуры на Go. Функциональных областей много: аутентификация, расписание/бронирование, биллинг, уроки, чаты (личные, групповые, комнатные), поддержка, отчёты/прогресс, нотификации, realtime-слой, медиа. Наивное разбиение «сервис на область» даёт 8–10 сервисов на старте — для MVP-команды это операционная нагрузка (деплой, мониторинг, контракты, миграции × N) без компенсирующей выгоды.

## Решение

Пять сервисов, граница = владение данными + протокольная роль:

1. **API Gateway** — REST-граница, без бизнес-логики.
2. **Auth** — идентичность, токены, JWKS.
3. **Billing** — леджер, холды; изолирован, потому что деньги требуют отдельного контура безопасности и аудита.
4. **Core Education** — всё предметное ядро: расписание, бронирования, уроки, **чаты, поддержка, отчёты, нотификации** — как внутренние пакеты с чистыми границами (`internal/scheduling`, `internal/booking`, `internal/chats`, `internal/reports`, ...).
5. **Realtime** — WebSocket-слой; выделен, потому что у него принципиально иной профиль: долгоживущие соединения, горизонтальное масштабирование, почти нет состояния.

Чаты, нотификации и отчёты **не выделяются** в сервисы на MVP. Критерий выделения в будущем — доказанная причина: иной профиль масштабирования, иной цикл релизов, иная команда. Пакетные границы внутри Core (свои таблицы, свой публичный интерфейс пакета) делают будущее выделение механическим.

## Альтернативы

- **Модульный монолит** (один Go-бинарь, пакеты `internal/auth`, `internal/billing`, ...). Честно быстрее для MVP, но gRPC-микросервисы — явная цель проекта (инженерная практика — часть ценности); кроме того, Billing-изоляция и независимое масштабирование Realtime полезны и сами по себе.
- **8–10 мелких сервисов** (Chat, Notification, Reporting, Media отдельно). Отклонено: каждый лишний сервис — сетевой хоп, контракт, деплой и точка отказа; Chat-сервис, например, превращает каждое сообщение в распределённую операцию «персист + нотификация + статус прочтения» через сеть без выгоды.

## Последствия

- (+) Мало операционной нагрузки; чёткие зоны владения данными; деньги и realtime изолированы.
- (+) Выделение пакета Core в сервис позже — механика, не переписывание (контракты уже protobuf, границы уже чистые).
- (−) Core — крупный сервис; дисциплина пакетных границ держится на ревью и линтерах (запрет импорта internal-пакетов друг друга мимо публичных интерфейсов).
- (−) Релиз любого пакета Core = релиз всего Core. Принимаем для MVP.
