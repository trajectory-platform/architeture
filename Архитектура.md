# Архитектура

## 1. Назначение документа

Документ описывает архитектуру платформы Trajectory на уровне, достаточном для планирования работ и оценки: состав сервисов и зоны их ответственности, способы взаимодействия, ключевые сквозные потоки, хранилища данных, модель доступа и нефункциональные требования.

Документ является продуктово-архитектурным: он фиксирует границы и решения, но не заменяет техническую документацию бэкенда (контракты, схемы БД, ADR, диаграммы), которая ведётся отдельно в репозитории бэкенда.

Термины — см. [Глоссарий](Глоссарий.md). Функциональный состав — см. [Верхнеуровневое ТЗ](Верхнеуровневое%20ТЗ.md) и [Требования к МВП версии](Требования%20к%20МВП%20версии.md).

## 2. Контекст системы

```
                    ┌──────────────────────────────┐
                    │        Пользователи          │
                    │  ученик · преподаватель ·    │
                    │        администратор         │
                    └───────────────┬──────────────┘
                                    │
              ┌─────────────────────┼─────────────────────┐
              │                     │                     │
        HTTPS / REST            WSS                   WebRTC
              │                     │                     │
              ▼                     ▼                     ▼
      ┌───────────────┐    ┌────────────────┐    ┌────────────────┐
      │  API Gateway  │    │   Realtime     │    │    LiveKit     │
      └───────┬───────┘    │    Service     │    │  (медиасервер) │
              │            └────────┬───────┘    └────────┬───────┘
              │  gRPC               │ gRPC                │ вебхуки
              ▼                     ▼                     ▼
      ┌──────────────────────────────────────────────────────────┐
      │   Auth · Core Education · Learning · Billing              │
      └──────────────────────────┬───────────────────────────────┘
                                 │
        ┌────────────┬───────────┼────────────┬─────────────┐
        ▼            ▼           ▼            ▼             ▼
   PostgreSQL     Redis    Шина событий   S3-хранилище   Платёжный
   (на сервис)               (Kafka)      (MinIO / S3)    шлюз (этап 2)
```

Внешние системы: медиасервер LiveKit (видео, аудио, запись), S3-совместимое объектное хранилище, OAuth-провайдеры, платёжный шлюз (подключается на завершающей стадии).

## 3. Архитектурные принципы

1. **Сервис = зона владения данными.** Каждый сервис владеет своей базой; межсервисные соединения таблиц запрещены. Доступ к чужим данным — только через API владельца или события.
2. **Минимальное число сервисов.** Новый сервис появляется только при доказанной причине: иной профиль масштабирования, иной цикл релизов или иная команда. «Концептуально отдельная область» причиной не является.
3. **REST на границе, gRPC внутри.** Клиент никогда не обращается к внутренним сервисам напрямую.
4. **Синхронно — когда нужен ответ сейчас; асинхронно — когда это свершившийся факт.** События публикуются только через транзакционный outbox, чтобы факт и его публикация не расходились.
5. **Деньги неизменяемы.** Баланс — результат вычисления по журналу операций, а не изменяемая колонка. Всё, что двигает деньги или создаёт брони, идемпотентно.
6. **Доступ проверяется по данным, а не только по роли.** Роль в токене отвечает на вопрос «кто это», членство в сущности — на вопрос «имеет ли он право на этот объект».
7. **Realtime-контур не хранит бизнес-состояние.** Экземпляры сервиса взаимозаменяемы; вся память — в хранилищах.
8. **Наблюдаемость с первого дня.** Сквозная трассировка от границы до последнего сервиса.

|---|---|---|---|---|---|
| **API Gateway** | — (без состояния) | REST | — | — | — |
| **Auth** | идентичности, пароли, сессии, refresh-токены, роли, разрешения, внешние аккаунты | — | регистрация, вход, обновление токена, выход, права | `user.registered`, `user.blocked` | — |
| **Core Education** | профили, доступность, слоты, брони, уроки, посещаемость, записи, чаты, уведомления, обращения | вебхуки LiveKit | расписание, брони, уроки, вход в комнату, чаты, уведомления, поддержка | `booking.confirmed`, `booking.cancelled`, `lesson.started`, `lesson.completed`, `lesson.recorded` | `user.registered`, `payment.captured`, `enrollment.expiring` |
| **Learning** | курсы, программы, темы, группы, зачисления и доступы, домашние задания, тесты, банк вопросов, материалы, прогресс | — | курсы, группы, зачисления, задания, тесты, материалы, прогресс | `homework.assigned`, `homework.submitted`, `homework.reviewed`, `enrollment.granted`, `enrollment.expiring`, `progress.milestone_reached` | `lesson.completed`, `payment.captured` |
| **Billing** | журнал операций, резервы, пакеты и абонементы, тарифы и комиссии, выплаты, ключи идемпотентности | — | резерв, списание, возврат, баланс, пополнение, покупка пакета, выплата | `payment.captured`, `hold.released`, `package.purchased`, `payout.completed` | `booking.cancelled`, `lesson.completed` |
| **Realtime** | журнал изменений доски, снимки, присутствие (эфемерно) | WebSocket | — | — | `lesson.started` |

### 4.1 API Gateway

Единственная внешняя точка входа для REST-запросов всех трёх клиентских приложений. Обязанности: терминирование REST и трансляция в gRPC, локальная проверка токена доступа по публичным ключам, проброс ключа идемпотентности, ограничение частоты запросов, единый формат ошибок, публикация спецификации API, из которой генерируется клиент для фронтенда.

Бизнес-логики не содержит. Если в обработчике шлюза появляется условие про предметную область — оно переезжает в профильный сервис.

### 4.2 Auth

Владеет идентичностью и доступом: регистрация, вход по email и паролю, вход через внешних провайдеров, восстановление пароля, сессии, обновление и отзыв токенов.

Здесь же живёт модель прав: роли (ученик, преподаватель, представитель, суперадминистратор, менеджер), совмещение нескольких ролей одним аккаунтом и гранулярные разрешения сотрудников административной панели. Разрешения выдаются в токене; проверка выполняется на шлюзе и в профильных сервисах.

Ключевое решение: **токены проверяются локально**. Auth подписывает токены асимметрично и публикует публичные ключи; шлюз и realtime-сервис проверяют подпись без сетевого вызова. Auth вызывается по сети только для входа, обновления и выхода.

### 4.3 Core Education

Предметное ядро: всё, что связано со временем и фактом занятия.

| Внутренний модуль | Ответственность |
|---|---|
| `profiles` | Профили пользователей; создаются по событию регистрации, редактируются владельцем |
| `scheduling` | Правила доступности, исключения, формирование слотов на скользящий горизонт |
| `booking` | Бронирование: защита от двойной брони, резервирование средств, подтверждение, перенос, отмена, регулярные брони |
| `lessons` | Жизненный цикл урока, вход в комнату, выдача токена комнаты и токена медиасервера, приём вебхуков LiveKit, посещаемость, завершение |
| `recordings` | Запуск и остановка записи, согласия участников, приём готовой записи, публикация как материала |
| `chats` | Личные, групповые чаты и чаты комнат: сообщения, вложения, статусы прочтения, поиск |
| `support` | Обращения: категории, приоритеты, статусы, назначение исполнителя |
| `notifications` | Формирование и доставка in-app уведомлений, лента, настройки пользователя, шаблоны |
| `outbox` | Публикация событий в шину в одной транзакции с изменением данных |

Core — авторитет по вопросу «кто имеет право войти в этот урок и этот чат».

### 4.4 Learning

Учебный контур: всё, что связано с содержанием обучения.

| Внутренний модуль | Ответственность |
|---|---|
| `courses` | Курсы, программы, темы, тарифы, публикация |
| `groups` | Группы, состав, вместимость (до 7 учеников) |
| `enrollments` | Зачисления, доступы на период, продление, прекращение, уведомление об истечении |
| `homework` | Задания, шаблоны, выдача, сдача, проверка, оценки, статусы |
| `tests` | Тесты, банк вопросов, попытки, автопроверка, ручная проверка, баллы, аттестации |
| `materials` | Библиотека материалов курса, темы и урока; приём записей и снимков доски |
| `progress` | Учёт занятий, посещаемости, заданий и тестов; освоение тем; журнал прогресса; достижения |

**Почему Learning выделен в отдельный сервис.** В первой версии архитектурной документации бэкенда учебный контур отсутствовал, и всё предметное ядро укладывалось в один сервис. С добавлением курсов, групп, домашних заданий, тестов, материалов и прогресса единый сервис получает более десяти внутренних модулей, две разные команды-владельца и два разных цикла релизов: контур расписания и уроков меняется редко и критичен к отказу, учебный контур меняется часто и переживает деградацию. Это и есть доказанная причина разделения по принципу 3.2.

Learning не знает о времени и статусе занятия напрямую — он реагирует на событие завершения урока.

### 4.5 Billing

Владеет деньгами и только деньгами.

- **Журнал операций** — записи списаний и зачислений; баланс = сумма по журналу. Записи не изменяются и не удаляются; исправление — компенсирующей записью.
- **Резервы** — блокировка средств под бронь: резерв при бронировании, списание при завершении урока, возврат при отмене.
- **Пакеты и абонементы** — предоплаченные наборы занятий и доступы на период; списание занятия из пакета при проведении урока.
- **Тарифы и комиссии** — цена занятия преподавателя, тариф курса, глобальная и индивидуальная комиссия платформы.
- **Выплаты** — баланс к выплате, реквизиты, запросы, обработка, история.
- **Идемпотентность** — ключ операции хранится в уникальном индексе; повтор с тем же ключом возвращает сохранённый результат.

Billing не знает про уроки и расписание: он оперирует резервами с внешним идентификатором брони. Связь «урок завершён → списать резерв» реализуется через событие.

Интеграция с платёжным шлюзом проектируется как **адаптер**: приём вебхука провайдера транслируется в пополнение баланса с идемпотентным ключом из идентификатора платежа. До подключения шлюза те же операции выполняет администратор.

### 4.6 Realtime

Терминирует WebSocket-соединения комнат и обслуживает три потока: доска, чат комнаты, присутствие.

| Компонент | Ответственность |
|---|---|
| WS-хаб | Подключение, проверка токена комнаты, маршрутизация сообщений по типам |
| Реестр комнат | Состав и присутствие участников в Redis с TTL; рассылка между экземплярами через Redis Pub/Sub |
| Журнал доски | Приём изменений доски, запись в журнал, рассылка остальным; при переподключении — снимок и хвост журнала |
| Пересылка чата | Немедленная рассылка сообщения участникам, затем асинхронное сохранение в Core |
| Уплотнение журнала | Периодическое слияние изменений в новый снимок, чтобы журнал не рос бесконечно |

Сервер не интерпретирует содержимое доски: изменения передаются как непрозрачные блоки, слияние выполняет клиентская библиотека. Падение экземпляра теряет только TCP-соединения — клиенты переподключаются к другому экземпляру, состояние комнаты восстанавливается из хранилищ.

### 4.7 Что не выделяем в отдельные сервисы

| Кандидат | Где живёт | Почему не сервис |
|---|---|---|
| Чаты | модуль в Core Education | Нет отдельного профиля масштабирования; выделение добавит сетевой вызов на каждое сообщение |
| Уведомления | модуль в Core Education | В MVP единственный канал — внутри приложения; выделять при добавлении внешних каналов |
| Поддержка | модуль в Core Education | Модель данных совпадает с чатами плюс статусы |
| Файлы | S3-совместимое хранилище + выдача подписанных ссылок в сервисах-владельцах | Байты не проходят через бэкенд |
| Медиа | LiveKit | Собственный SFU не является задачей проекта |
| Отчётность | модули в Core Education и Learning | На объёмах MVP отдельное хранилище отчётов избыточно |

## 6. Взаимодействие

| Канал | Кто использует | Назначение |
|---|---|---|
| REST через шлюз | Все клиентские приложения | Запрос-ответные операции: профили, расписание, брони, задания, материалы, финансы, админ-панель |
| WebSocket | Клиенты в комнате урока, лента уведомлений | Доска, чат комнаты, присутствие, живые обновления |
| WebRTC | Клиенты в комнате урока | Аудио, видео, демонстрация экрана — напрямую с медиасервером, минуя бэкенд |
| gRPC | Сервисы между собой | Синхронные вызовы, когда нужен ответ сейчас |
| Шина событий | Сервисы между собой | Асинхронные факты: подтверждение брони, завершение урока, списание, выдача задания |
| Вебхуки | LiveKit → Core, платёжный шлюз → Billing | Внешние факты; подпись запроса проверяется до обработки |

**Правило публикации событий.** Событие пишется в таблицу `outbox` в той же транзакции, что и доменное изменение; отдельный процесс публикует его в шину. Это исключает ситуации «изменение есть, события нет» и наоборот.

**Правило потребления событий.** Доставка гарантируется «хотя бы один раз», поэтому все обработчики идемпотентны: повторная доставка не создаёт дубликатов.

## 7. Ключевые сквозные потоки

### 7.1 Бронирование занятия

1. Клиент отправляет запрос на бронирование с ключом идемпотентности.
2. Core Education в транзакции проверяет доступность слота и создаёт бронь в состоянии «ожидает». Ограничение на пересечение интервалов времени преподавателя не даст создать вторую бронь на то же время даже при гонке запросов.
3. Core вызывает Billing для резервирования средств. Если средств недостаточно — бронь отклоняется, слот освобождается.
4. Во второй транзакции бронь переводится в состояние «подтверждена», создаётся урок, публикуется событие подтверждения.
5. При неизвестном исходе шага 3 (таймаут) сверяющий процесс повторяет вызов с тем же ключом идемпотентности — повторного резервирования не произойдёт.

### 7.2 Вход в комнату урока

1. Клиент запрашивает вход в урок.
2. Core проверяет членство пользователя в уроке и попадание текущего времени в окно занятия.
3. Core выдаёт короткоживущий токен комнаты (для WebSocket) и токен медиасервера с правами только на эту комнату.
4. Клиент подключается к Realtime по WebSocket и к LiveKit по WebRTC.
5. Realtime и LiveKit не обращаются к базам за правами — достаточно подписи токена.

### 7.3 Синхронизация доски

1. Клиент при подключении отправляет своё состояние; сервер отвечает снимком и недостающим хвостом журнала.
2. Каждое локальное изменение отправляется на сервер, записывается в журнал комнаты и рассылается остальным участникам.
3. При обрыве соединения клиент продолжает работать локально; при переподключении отправляет накопленные изменения и догружает пропущенные.
4. Изменения коммутативны и идемпотентны: порядок доставки не влияет на итоговое состояние, повторная доставка безопасна.
5. По достижении порога журнал уплотняется в новый снимок.

### 7.4 Завершение занятия

1. Медиасервер присылает вебхук о завершении комнаты; либо преподаватель завершает занятие вручную; либо срабатывает автозавершение по времени.
2. Core фиксирует статус «завершён», посещаемость и длительность, публикует событие завершения.
3. Billing списывает резерв: с баланса ученика — стоимость, преподавателю — вознаграждение за вычетом комиссии; публикует событие о списании.
4. Learning увеличивает счётчики прогресса, отмечает освоение темы и при достижении контрольной точки создаёт запись журнала прогресса.
5. Core помечает урок оплаченным по событию списания.

Потребители независимы: задержка одного не блокирует остальных.

### 7.5 Запись занятия

1. Преподаватель запускает запись; система запрашивает согласие участников и фиксирует его.
2. Core отдаёт медиасерверу команду начать запись; участникам показывается индикатор.
3. По завершении занятия медиасервер сохраняет файл в объектное хранилище и присылает вебхук.
4. Core публикует событие о готовности записи; Learning добавляет её в материалы урока.
5. По истечении срока хранения запись удаляется фоновым процессом.

### 7.6 Домашнее задание

1. Преподаватель создаёт задание в Learning и выдаёт его ученику или группе.
2. Learning публикует событие о выдаче; Core формирует уведомление ученику.
3. Ученик загружает файлы напрямую в объектное хранилище по подписанной ссылке и отправляет работу.
4. Learning фиксирует сдачу, публикует событие; Core уведомляет преподавателя.
5. Преподаватель проверяет, ставит оценку; Learning обновляет прогресс и публикует событие; Core уведомляет ученика.

### 7.7 Отмена занятия

1. Инициатор отменяет бронь; Core вычисляет политику возврата по сроку до занятия и инициатору.
2. Core переводит бронь и урок в состояние «отменён» и публикует событие с рассчитанной политикой.
3. Billing возвращает резерв полностью или частично, при частичном возврате добавляя записи удержания.
4. Слот освобождается и снова доступен для бронирования.

## 8. Данные и хранилища

| Хранилище | Что хранит |
|---|---|
| `auth_db` | Идентичности, учётные данные, сессии, refresh-токены, роли и разрешения, привязки внешних аккаунтов |
| `education_db` | Профили, правила доступности, слоты, брони, уроки, посещаемость, записи, чаты и сообщения, обращения, уведомления, outbox |
| `learning_db` | Курсы, программы, темы, группы, зачисления, задания и сдачи, тесты и попытки, банк вопросов, материалы, прогресс, outbox |
| `billing_db` | Журнал операций, резервы, пакеты, тарифы и комиссии, выплаты, ключи идемпотентности, outbox |
| `realtime_db` | Журнал изменений доски, снимки |
| Redis | Присутствие и состав комнат, кэш, ограничение частоты запросов, рассылка между экземплярами |
| Объектное хранилище | Аватары, вложения чатов, файлы домашних работ, материалы, записи занятий, снимки доски |

Ключевые инварианты:

1. **Двойное бронирование невозможно** — ограничение на пересечение временных интервалов преподавателя на уровне БД.
2. **Урок и бронь связаны один к одному**; урок создаётся при подтверждении брони.
3. **Журнал операций только дополняется** — на уровне прав доступа к БД у сервиса нет прав на изменение и удаление записей.
4. **Баланс воспроизводим на любой момент времени** пересчётом по журналу.
5. **Прогресс не задваивается** — факт учёта занятия фиксируется отдельной записью с уникальным ключом.
6. **Ссылки между сервисами — идентификаторы без внешних ключей**; целостность обеспечивается событиями и сверяющими процессами.

## 9. Модель доступа и безопасность

| Уровень | Механизм |
|---|---|
| Аутентификация | Токен доступа с коротким сроком жизни, refresh-токен с ротацией и детектом повторного использования |
| Проверка токена | Локально по опубликованным публичным ключам, без сетевого вызова на каждый запрос |
| Роль и разрешения | В токене: массив ролей и, для сотрудников, объединённый список разрешений их административных ролей |
| Доступ к объекту | По членству в данных: участник урока, участник чата, владелец задания, зачисленный на курс |
| Доступ в комнату | Короткоживущий токен комнаты, выданный после проверки членства и окна времени |
| Доступ к файлу | Подписанная ссылка, выдаваемая только после проверки прав на объект |
| Денежные операции | Обязательный ключ идемпотентности; повтор с тем же ключом и другим телом отклоняется |
| Действия администратора | Фиксация в журнале действий с указанием исполнителя, объекта и причины |
| Ограничение частоты | На входе и регистрации, восстановлении пароля, отправке сообщений, загрузке файлов |

**Персональные данные и записи занятий.** Запись ведётся только после явного согласия участников; факт согласия хранится. Для записей задаётся срок хранения и предусмотрено удаление по запросу. Персональные данные не пишутся в логи; доступ сотрудников к персональным данным ограничен разрешениями и журналируется.

## 10. Фронтенд-архитектура

Клиентская часть — три приложения на общей кодовой базе:

| Приложение | Пользователь | Характер интерфейса |
|---|---|---|
| Кабинет преподавателя | преподаватель | Плотный рабочий интерфейс: таблицы, фильтры, боковые панели, массовые действия |
| Кабинет ученика | ученик | Упрощённый интерфейс, крупные акценты, элементы геймификации |
| Административная панель | сотрудник платформы | Табличный интерфейс управления с поиском, фильтрами и журналами |

Общие решения:

- **React и TypeScript**, библиотека **SteroidsJS** как основа приложения: маршрутизация, формы, работа с API, слой данных. Кастомизация выполняется заменой представлений и переопределением стилей, а не форком библиотеки.
- **Единая дизайн-система**: токены цвета, типографики, отступов и радиусов; светлая и тёмная темы; общий набор компонентов. Кабинеты различаются композицией и плотностью, а не разными наборами компонентов.
- **Клиент API генерируется** из спецификации, публикуемой шлюзом — контракт не расходится с бэкендом.
- **Комната урока — отдельный модуль** с собственным жизненным циклом: WebSocket-соединение, CRDT-документ доски, подключение к медиасерверу, обработка потери связи и переподключения.
- **Адаптивность** обязательна для кабинета ученика; кабинет преподавателя и админ-панель оптимизированы под десктоп с работоспособной мобильной версией ключевых сценариев.

## 11. Нефункциональные требования

### 11.1 Производительность и масштаб

| Показатель | Целевое значение |
|---|---|
| Одновременно идущих уроков | 100 |
| Одновременных участников комнат | до 800 |
| Участников одной комнаты | до 8 |
| Активных учеников | 2 000 – 5 000 |
| Преподавателей | ~100 |
| Время отклика REST-операций (95-й перцентиль) | до 300 мс |
| Задержка доставки изменения доски | до 200 мс в пределах региона |
| Время восстановления состояния доски после переподключения | до 2 с |
| Время входа в комнату от нажатия до готовности медиа | до 5 с |

### 11.2 Надёжность

- Отказ экземпляра realtime-сервиса не приводит к потере содержимого доски: клиенты переподключаются, состояние восстанавливается из журнала.
- Отказ Billing не блокирует проведение уже подтверждённых занятий; списание выполнится после восстановления по событию.
- Отказ Learning не блокирует проведение занятий; прогресс и задания догоняют состояние после восстановления.
- Все обработчики событий идемпотентны, повторная доставка безопасна.
- Резервное копирование баз данных и объектного хранилища; проверка восстановления.

### 11.3 Безопасность

Требования перечислены в разделе 9 и в [Требованиях к МВП версии](Требования%20к%20МВП%20версии.md), разделы 2 и 3.

### 11.4 Наблюдаемость

- Сквозная трассировка запроса от REST-границы через все вызовы сервисов.
- Метрики: количество уроков в статусах, срывы входа в комнату, задержки доставки изменений доски, глубина очереди событий, отставание потребителей, длительность денежных операций, ошибки вебхуков.
- Логи с корреляционным идентификатором запроса; персональные данные не логируются.
- Оповещения: рост отказов входа в комнату, отставание потребителя событий, зависшие брони в состоянии «ожидает», зависшие резервы, ошибки записи занятий.

### 11.5 Эксплуатация

- Отдельные стенды: разработка, тестирование, продуктив.
- Автоматические миграции баз данных при развёртывании.
- Развёртывание сервисов независимо друг от друга; обратная совместимость контрактов в пределах одного релизного цикла.
- Конфигурация и секреты — во внешнем хранилище, не в образах.

## 12. Отношение к первой версии архитектурной документации бэкенда

В репозитории бэкенда существует более ранняя версия архитектурной документации (пять сервисов, только индивидуальные занятия, внутренний баланс без платёжного шлюза, отсутствие учебного контура). Настоящий документ развивает её. Отличия:

| Тема | Первая версия | Настоящий документ |
|---|---|---|
| Формат занятий | Только индивидуальные | Индивидуальные и мини-группы до 8 участников |
| Учебный контур | Отсутствует | Выделен сервис Learning: курсы, группы, задания, тесты, материалы, прогресс |
| Продуктовая модель | Маркетплейс со свободным бронированием | Гибрид: свободное бронирование и организованное зачисление администратором |
| Запись занятий | Не рассматривалась | Входит в MVP, включая согласие и сроки хранения |
| Деньги | Внутренний баланс, пополнение администратором | Полный контур: пакеты, абонементы, комиссия, выплаты; шлюз — адаптером на завершающей стадии |
| Вход в систему | Email и пароль | Email и пароль плюс внешние провайдеры |
| Права администратора | Единая роль | Гранулярные разрешения по разделам |

Технические решения первой версии, сохранённые без изменений: локальная проверка токенов по публичным ключам, транзакционный outbox, идемпотентность денежных операций, ограничение на пересечение временных интервалов для защиты от двойного бронирования, CRDT-подход к доске с сервером-транспортом, использование готового медиасервера.

## 13. Открытые вопросы

1. Правила расчёта стоимости группового занятия: фиксированная цена с ученика или деление стоимости занятия между участниками.
2. Поведение группового занятия при неявке части учеников: списывать ли с отсутствовавших.
3. Требуется ли сохранение доски между занятиями одного курса (сквозная доска) или доска создаётся заново на каждый урок.
4. Глубина хранения записей занятий и её влияние на стоимость хранилища.
5. Необходимость отдельного сервиса уведомлений при добавлении внешних каналов на этапе 2.
6. Выбор конкретного платёжного провайдера и требований фискализации.
