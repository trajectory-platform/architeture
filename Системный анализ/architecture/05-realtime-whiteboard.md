# 05 — Realtime и вайтборд

Комната урока объединяет три потока: медиа (LiveKit, WebRTC), состояние доски (Yjs поверх WebSocket) и события комнаты (чат, presence — тот же WebSocket). Каждый урок получает новую доску с собственным `lesson_id`; доска предыдущего урока не переиспользуется. Этот документ описывает realtime-слой; решение по CRDT зафиксировано в [ADR-002](../adr/ADR-002-crdt-sync-path-a.md).

## Почему сервер не интерпретирует CRDT

У Yjs нет зрелой серверной реализации на Go. Но она и не нужна — ключевые свойства Yjs-апдейтов:

- **Коммутативность** — порядок применения не влияет на итоговое состояние;
- **Идемпотентность** — повторное применение апдейта безвредно;
- **Самодостаточность** — апдейт — бинарный блоб, который любой Yjs-клиент применяет без контекста сервера.

Следовательно, серверу достаточно быть **relay с персистентностью**: принять блоб, дописать в лог комнаты, разослать остальным участникам. Слияние и разрешение конфликтов происходят на клиентах — детерминированно и одинаково у всех. Сервер не может «неправильно смержить», потому что не мержит вовсе.

## Протокол WebSocket

Одно WSS-соединение на участника комнаты. Подключение: `wss://.../rooms/{lesson_id}?token=<room JWT>` — короткоживущий токен, выданный Core при `JoinLesson` ([07 — Безопасность](07-security.md)). Сообщения — envelope с типом:

| Тип | Направление | Содержание |
|---|---|---|
| `board.update` | клиент ⇄ сервер | Yjs-апдейт (opaque bytes) |
| `board.sync_request` | клиент → сервер | state vector клиента — запрос догона |
| `board.sync_response` | сервер → клиент | snapshot + tail (см. ниже) |
| `chat.message` | клиент ⇄ сервер | сообщение чата комнаты |
| `presence.update` | клиент ⇄ сервер | курсор, активный инструмент, online-статус |
| `room.event` | сервер → клиент | участник вошёл/вышел, урок завершается |

## Путь апдейта доски

Диаграмма: [whiteboard-sync.puml](../diagrams/sequence/whiteboard-sync.puml).

1. Клиент A рисует штрих → Yjs кодирует инкрементальный апдейт (десятки байт) → `board.update` в WebSocket.
2. Realtime-инстанс: **append** в лог комнаты (`board_updates`, см. [06](06-data-storage.md)) → **publish** в Redis-канал комнаты.
3. Все инстансы realtime, держащие участников этой комнаты, получают апдейт из Redis и **broadcast** в свои WebSocket-соединения (кроме отправителя).
4. Клиент B применяет апдейт к своему Y.Doc — состояние сходится.

Порядок шагов 2: сначала персистентность, потом fan-out — апдейт, который увидел другой участник, уже не может потеряться при падении инстанса.

## Reconnect и восстановление

Обрыв соединения — штатный режим (мобильные сети, смена Wi-Fi):

1. Клиент переподключается (к любому инстансу realtime — они равнозначны) и шлёт `board.sync_request` со своим **state vector** (компактное описание «что я уже видел», стандартный механизм Yjs).
2. Сервер отвечает `board.sync_response`: **последний снапшот + все апдейты после него** (snapshot + tail). Сервер не вычисляет дифф по state vector — он не интерпретирует блобы; он шлёт надмножество, а клиентский Yjs идемпотентно отбрасывает уже применённое.
3. Локальные правки, сделанные клиентом офлайн, Yjs отправляет после синхронизации — конфликты разрешает CRDT.

Тот же поток — холодный вход нового участника (state vector пустой) и восстановление после падения realtime-инстанса.

## Компакция лога

Лог апдейтов растёт с каждым штрихом; replay тысяч апдейтов при входе — медленно. Снапшот = слитое состояние документа (`Y.encodeStateAsUpdate`). Две стратегии:

1. **Node-сайдкар** (основная): маленький воркер на Node/TS периодически (или по порогу: N апдейтов / M байт с последнего снапшота) читает snapshot + tail, выполняет `Y.mergeUpdates`, пишет новый снапшот. Апдейты до снапшота можно удалять (или архивировать в MinIO для history/replay).
2. **Снапшот с клиента** (упрощённая, без сайдкара): клиент преподавателя периодически шлёт `Y.encodeStateAsUpdate` своего документа как снапшот. Дешевле инфраструктурно; минус — зависимость от присутствия и честности клиента, поэтому подходит как временная мера MVP.

Снапшот — оптимизация чтения. Корректность от него не зависит: потеря снапшота лечится replay'ем полного лога. После завершения урока финальный snapshot публикуется как материал урока; следующий урок начинает отдельный пустой Y.Doc.

## Presence и масштабирование realtime

- Membership/presence комнат — TTL-ключи в Redis (`room:{id}:members`), heartbeat от инстансов.
- Fan-out между инстансами — Redis Pub/Sub (здесь он уместен: потеря presence-сообщения не критична, а board-апдейты уже персистентны в логе до broadcast).
- Инстанс упал → клиенты переподключаются к другому через Nginx; новый инстанс подписывается на Redis-каналы комнаты и отдаёт snapshot + tail. Состояние не теряется, т.к. в самом инстансе его нет.

## Медиа: LiveKit

Видео/аудио/screen share не касаются нашего бэкенда — клиент соединяется с LiveKit (SFU) напрямую по WebRTC. Интеграция в трёх точках (диаграмма: [lesson-join.puml](../diagrams/sequence/lesson-join.puml)):

1. **Вход**: `POST /lessons/{id}/join` → Core проверяет членство и временное окно → минтит **LiveKit access token** (server SDK, права publish/subscribe на комнату) и **room JWT** для WebSocket → клиент устанавливает оба соединения.
2. **Вебхуки**: `participant_joined`, `participant_left`, `room_finished` → HTTP-эндпоинт Core (подпись вебхука проверяется) → посещаемость, фактический таймер урока, триггер `lesson.completed`.
3. **Завершение**: «End lesson» от преподавателя → Core закрывает комнату через LiveKit API → `room_finished` → штатная цепочка завершения ([04](04-sagas-and-consistency.md)).

## Чат комнаты

`chat.message` рассылается участникам немедленно (latency-first), затем инстанс realtime асинхронно персистит его в Core по gRPC (`SaveMessage`) с client-generated `message_id` — ретраи не создают дублей. История чата комнаты после урока доступна через обычный REST (`GET /lessons/{id}/messages`) — данные у Core, как и все остальные чаты ([02 — Сервисы](02-services.md)).
