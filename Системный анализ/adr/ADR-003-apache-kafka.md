# ADR-003 — Шина событий: Apache Kafka + transactional outbox

**Статус**: принято  
**Дата**: 2026-06-11  
**Изменено**: 2026-09-04

## Контекст

Ключевые цепочки системы завязаны на надёжную доставку фактов между сервисами: `lesson.completed` приводит к захвату холда в Billing, `booking.cancelled` — к возврату резерва, а Notification материализует пользовательские уведомления. Redis Pub/Sub не подходит: нет персистентности, подтверждения обработки и повторной доставки. При недоступности потребителя событие потеряется.

Первоначально для MVP был выбран NATS JetStream из-за простой эксплуатации. После уточнения целевой архитектуры принято использовать знакомую команде платформу событий с большим запасом масштабирования, развитой экосистемой наблюдаемости и стандартной моделью consumer groups.

## Решение

Использовать два уровня надёжности:

1. **Apache Kafka в режиме KRaft** как межсервисную шину событий. Семантика обработки — at-least-once. Каждый сервис-потребитель использует отдельную consumer group и обязан обрабатывать повторную доставку идемпотентно.
2. **Transactional outbox** на стороне издателя. Сервис сохраняет событие в своей Postgres в одной транзакции с доменным изменением. Outbox relay публикует событие в Kafka и только после подтверждения брокера отмечает запись опубликованной.

События распределяются по доменным topics:

- `trajectory.auth.events.v1`;
- `trajectory.education.events.v1`;
- `trajectory.learning.events.v1`;
- `trajectory.billing.events.v1`;
- `trajectory.notification.events.v1`.

Envelope содержит `event_id`, `event_type`, `occurred_at`, `schema_version`, `producer`, protobuf payload и безопасные tracing headers. Kafka message key — стабильный `aggregate_id`. Поэтому события одного агрегата попадают в одну partition и сохраняют порядок. Глобальный порядок между агрегатами не гарантируется и не требуется.

Outbox producer использует `acks=all` и idempotent producer. В production topics имеют replication factor не ниже 3 и `min.insync.replicas=2`. Локальная среда может использовать один broker без изменения контрактов.

Consumer фиксирует offset только после успешной транзакции своей БД. В той же транзакции сохраняется `event_id` в `processed_events` либо создаётся доменная запись с уникальным ключом события. Kafka offset не используется как ключ идемпотентности.

После ограниченного числа попыток poison message публикуется в `trajectory.dlq.<service>.<consumer>`. DLQ содержит исходный безопасный payload либо только redacted metadata по политике события. После подтверждения DLQ producer consumer фиксирует offset исходного сообщения. Replay выполняется отдельной операторской операцией с audit record.

**Redis остаётся** для кэша, presence, rate limiting и быстрого fan-out board updates между инстансами Realtime. Эти данные эфемерны либо восстанавливаются из Postgres.

## Альтернативы

- **NATS JetStream.** Функционально достаточен и проще для малого окружения. Отклонён после пересмотра: команда лучше знакома с Kafka, а развитая модель partitions, consumer groups, retention и replay соответствует планируемому росту нагрузки и числа потребителей.
- **Redis Pub/Sub.** Отклонён: fire-and-forget не обеспечивает персистентность, подтверждение обработки и redelivery.
- **Redis Streams.** Отклонён: смешивает жизненный цикл кэша и durable event log, уступает Kafka по экосистеме эксплуатации и масштабированию.
- **Синхронные gRPC-вызовы вместо событий.** Отклонены: связывают доступность сервисов и требуют собственной персистентной очереди ретраев.

## Последствия

- (+) События переживают недоступность потребителя; lag видим и управляем.
- (+) Partitions и consumer groups дают горизонтальное масштабирование потребителей.
- (+) Retention позволяет подключать новые projections и выполнять контролируемый replay.
- (+) Добавление Notification и аналитических потребителей не меняет издателей.
- (−) Kafka требует больше ресурсов и операционной компетенции, чем NATS JetStream.
- (−) Нужно управлять количеством partitions, replication, retention, rebalance и совместимостью схем.
- (−) At-least-once требует идемпотентности каждого consumer.
- (−) Outbox relay остаётся шаблонным компонентом каждого сервиса-издателя.
- (−) Порядок гарантируется только внутри partition. Producer обязан использовать стабильный `aggregate_id` как message key.
