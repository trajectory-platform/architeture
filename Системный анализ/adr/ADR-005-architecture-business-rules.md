# ADR-005 — Границы публичного API и контрактные инварианты

**Статус:** принято
**Дата:** 2026-07-08
**Изменено:** 2026-09-04

## Контекст

Публичный REST API — единственная синхронная граница для Web/App-клиентов. За ней находятся сервисы с разными владельцами данных и разной моделью согласованности: Auth, Core Education, Learning, Billing и Notification. Без единых правил Gateway начинает дублировать доменную логику, API расходится с gRPC-контрактами, а повтор сетевого запроса может создать лишнюю бронь или платёж.

Нужно зафиксировать именно архитектурные инварианты API. Конкретные продуктовые политики — минимальная цена, длительность урока, правила отмены и допустимые каналы уведомлений — изменчивы; они не являются предметом ADR и должны жить в документации владельца домена и в его конфигурации.

## Решение

1. **Контрактом владеет отдельный репозиторий `contracts`.** В нём хранятся versioned Protobuf-контракты, payload'ы доменных событий и OpenAPI-спеки Gateway. Сервисы подключают его как версионированный Go-модуль; они не импортируют код или `internal` другого сервиса. Совместимость проверяется `buf breaking` для Protobuf и OpenAPI-lint/diff для REST.
2. **Gateway — транспортная граница, не владелец правил.** Он аутентифицирует запрос, применяет rate limit, валидирует синтаксис и переводит REST в gRPC. Авторизация ownership, цены, доступность слота, денежные проводки и выбор получателей уведомлений остаются у сервисов-владельцев.
3. **Деньги и резервирование требуют сквозной идемпотентности.** Каждый внешний небезопасный запрос с денежным эффектом или созданием/изменением брони несёт `Idempotency-Key`. Gateway передаёт его в gRPC metadata; Core и Billing сохраняют ключ вместе с хэшем канонического запроса и возвращают исходный результат при повторе. Один и тот же ключ с иным телом даёт `409 Conflict`.
4. **Единые значения и ошибки.** Суммы передаются только целыми minor units (`int64` в gRPC; `integer` с `int64`-диапазоном в OpenAPI). Временные точки — RFC 3339 UTC, календарные правила — IANA timezone. Все коллекции используют cursor-пагинацию с ограниченным `limit`; успешный список возвращается вместе с `next_cursor`. Ошибки имеют один конверт `{code, message, details?, trace_id}` и документированные статусы.
5. **Файлы загружаются напрямую в object storage.** Gateway выдаёт только короткоживущий presigned URL после проверки прав, размера, заявленного типа и назначения файла. Объект получает серверный ключ, не управляемый клиентом. Фактическая проверка содержимого, антивирусная обработка и публикация выполняются до того, как объект становится доступен другим пользователям.
6. **Уведомления асинхронны.** Доменные сервисы публикуют факты через transactional outbox; Notification Service сам определяет каналы и доставляет сообщение с дедупликацией. Ни один пользовательский REST-запрос не ждёт отправки email, push или внешнего провайдера.
7. **Цена и денежный outcome передаются snapshot'ом.** Для каждого ученика бронь фиксирует отдельные сумму, валюту и `hold_reference_id`. Core применяет текущую cancellation policy и передаёт Billing уже вычисленные суммы capture/release. Billing не читает тарифы, посещаемость или расписание другого сервиса.
8. **Границы учебного контура явны.** Core владеет временем, уроком и attendance. Learning владеет курсами, заданиями, материалами и progress. Их projections сходятся через идемпотентные Kafka events; REST-клиент не оркестрирует эту согласованность.

## Последствия

### Положительные

- Повторы запросов не создают повторных броней или движений денег.
- Цена каждого ученика остаётся воспроизводимой после изменения тарифа, а Billing не дублирует cancellation policy.
- Внешний контракт остаётся совместимым и проверяемым независимо от релизов сервисов.
- Медленные, недоступные или лимитирующие внешние провайдеры уведомлений не увеличивают latency критических пользовательских потоков.
- Контракт ясно отделяет транспортную валидацию от бизнес-правил, поэтому Gateway не превращается в скрытый BFF/монолит.

### Отрицательные

- Нужно поддерживать версионирование контрактов, контрактные тесты и миграции клиентов.
- Cursor-пагинация и идемпотентные ключи усложняют SDK и фронтенд по сравнению с простыми массивами и `offset`.
- Прямая загрузка файлов требует отдельного асинхронного pipeline проверки и понятных клиенту статусов.
- Доставка уведомлений имеет семантику at-least-once; идемпотентность и дедупликация обязательны.

## Альтернативы

- **Хранить правила в Gateway/OpenAPI.** Отклонено: такие правила становятся дубликатами доменной логики и меняются несогласованно.
- **Делать upload через Gateway.** Отклонено: gateway становится дорогой data plane и точкой риска OOM/DoS.
- **Вызывать провайдеров уведомлений синхронно из Core/Billing.** Отклонено: доступность и latency внешнего провайдера не должны определять исход бронирования или платежа.
- **Не требовать идемпотентность и полагаться на retry клиента.** Отклонено: сетевые ретраи неизбежны, а последствия повторной денежной операции неприемлемы.
