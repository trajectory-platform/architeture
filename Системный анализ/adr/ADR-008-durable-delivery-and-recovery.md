# ADR-008 — Подтверждение сохранения и восстановление первого среза

**Статус:** принято для документационной базы; выполнение проверяется по release evidence
**Дата:** 2026-09-05

## Контекст

MVP 1.0 уже требует confirmation/reset email, идемпотентных денег, сохранения чата и восстановления доски. Стадийность откладывает группы, OAuth и записи, но не корректность включённых сценариев. Kafka и семь сервисов сохраняются по ADR-001/003/007.

## Решение

1. Auth хранит hash для проверки action token и отдельно короткоживущий зашифрованный delivery payload, достаточный для повторной отправки после рестарта. Payload создаётся атомарно с action request/outbox. Notification получает его только по защищённому RPC; секрет не попадает в Kafka/DLQ/логи. Чтение не потребляет action token. Истечение, потребление/отзыв request или подтверждённое завершение доставки очищает payload; resend после очистки создаёт новый request и отзывает старый. Повтор отправки до подтверждения допустим и возвращает ту же ссылку.
2. Billing сериализует проверку и изменение доступных средств по постоянной строке account с `SELECT FOR UPDATE` в одной транзакции. Все расходы/холды/корректировки следуют этому протоколу; несколько account блокируются в стабильном порядке. Баланс остаётся вычисляемым из журнала и ACTIVE holds.
3. Core авторизует и сохраняет chat message до durable ack/broadcast. Realtime не обещает надёжную доставку очереди в памяти. Клиент повторяет pending message с тем же ID; история Core является способом восстановления пропущенного broadcast.
4. Realtime хранит постоянный `board_rooms.last_seq`, увеличиваемый атомарно с append. Согласованная пара snapshot + tail покрывает диапазон до зафиксированного high-water mark. После удаления покрытых updates snapshot становится обязательной частью состояния; только проверенная атомарная публикация позволяет удаление. Недоверенный клиентский snapshot не разрешает pruning.
5. Redis Pub/Sub остаётся ускорителем fan-out. Durable ack содержит seq; heartbeat/high-water и переподписка запускают resync, если live-сообщение потеряно. Подписка/buffering до чтения consistent snapshot устраняет окно между snapshot и live.
6. Core владеет состоянием урока. LiveKit webhook — наблюдение, сохраняемое идемпотентно по event ID. EndLesson и scheduled reconciliation не зависят от доставки `room_finished`. Денежное решение требует policy snapshot; технически неоднозначные исходы требуют разбора, а не неявного capture.

## Альтернативы

- Оставить delivery secret только в памяти Auth — не переживает рестарт между commit и отправкой.
- Broadcast чата до сохранения — допустим лишь как локальный optimistic UI, не как подтверждённое сообщение.
- Считать уникальный idempotency key защитой баланса — не защищает два независимых расхода.
- Считать Redis publish и room webhook гарантированными — оставляет пропуски без reconciliation.
- Заменить Kafka, Go relay или весь сервисный состав — не требуется для исправления перечисленных гарантий.

## Последствия

- Добавляются forward-only migrations для account, delivery payload и board high-water; существующие миграции не редактируются.
- Сохраняются PostgreSQL per service, Kafka outbox, S3 API и выбранные release boundaries.
- До полного RBAC нужны минимальные серверные ограничения seed staff; до полного hardening нужны fault tests уже реализованных путей.
- Увеличивается объём критических проверок 1.0, но не добавляются отложенные пользовательские функции. Проверки и открытые политики перечислены в [09 — Релизная готовность](../architecture/09-release-readiness.md).
