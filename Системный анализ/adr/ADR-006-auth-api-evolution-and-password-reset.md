# ADR-006 — Эволюция Auth API и владение восстановлением пароля

**Статус:** принято
**Дата:** 2026-09-04

## Контекст

Исходный план T02 определял минимальный контракт `auth.v1`: RPC `Register`, `Login` и `Refresh` напрямую возвращали `TokenPair`; `Role` содержал только `ROLE_STUDENT` и `ROLE_TEACHER`; событие `UserRegistered` не имело отдельного `event_id`; восстановление пароля не входило в контракт и схему Auth Service.

При реализации контракт расширился. Для ответов аутентификации понадобились точки расширения, общая модель роли должна представлять административную identity, а обработчикам событий нужен стабильный ключ идемпотентности, не зависящий от JetStream delivery sequence. Восстановление пароля также требует явного владельца состояния и безопасной границы с Notification Service.

Эти изменения считаются сознательной эволюцией исходного T02, а не случайным расхождением реализации с планом. ADR фиксирует текущую базовую форму `v1` до её стабильной публикации. После публикации несовместимые изменения по-прежнему требуют новой версии контракта согласно ADR-004 и ADR-005.

## Решение

1. **RPC аутентификации возвращают отдельные response wrappers.** `Register`, `Login` и `Refresh` возвращают соответственно `RegisterResponse`, `LoginResponse` и `RefreshResponse`; каждый wrapper содержит `TokenPair tokens`. Новые метаданные конкретного сценария можно добавлять в wrapper совместимыми полями, не расширяя общий `TokenPair` и не меняя форму других RPC.
2. **`ROLE_ADMIN` входит в общий enum `Role`, но недоступен для self-register.** Контракт использует единый набор ролей identity: `ROLE_STUDENT`, `ROLE_TEACHER`, `ROLE_ADMIN`. RPC `Register` принимает только `ROLE_STUDENT` и `ROLE_TEACHER`; `ROLE_ADMIN`, `ROLE_UNSPECIFIED` и неизвестные значения отклоняются прикладной валидацией. Административные identity создаются только доверенным операционным потоком вне публичной регистрации.
3. **Восстановлением пароля владеет Auth Service.** Auth предоставляет `RequestPasswordReset` и `ResetPassword`. Первый RPC всегда возвращает одинаковый успешный ответ независимо от существования email. Второй атомарно проверяет одноразовый token, меняет credential, помечает reset request использованным и отзывает все refresh-token families пользователя. Internal RPC `GetPasswordResetDelivery` доступен только Notification Service через доверенную service-to-service аутентификацию.
4. **Состояние восстановления хранится в `auth_db`.** Таблица `password_reset_requests` принадлежит Auth Service и связывает reset request с identity. В БД хранится только SHA-256 hash одноразового token, его TTL и `used_at`; raw token не хранится в открытом виде. Auth отвечает за создание, проверку, одноразовость, истечение и потребление reset request.
5. **События восстановления не переносят секрет.** Auth публикует `password.reset.requested` через transactional outbox. Payload содержит ссылочные данные, включая `reset_request_id`, но не raw token и не готовый reset URL. Notification Service получает данные для доставки через защищённый `GetPasswordResetDelivery`; секрет не попадает в JetStream, обычные логи или DLQ.
6. **`UserRegistered.event_id` является стабильным ключом события.** Auth создаёт новый UUID для логического события при регистрации и сохраняет payload в outbox в одной транзакции с identity. Повторная публикация той же outbox-записи сохраняет тот же `event_id`. Consumers используют `event_id` для идемпотентной обработки и дедупликации redelivery.

## Альтернативы

- **Возвращать `TokenPair` напрямую.** Отклонено: любое поле, специфичное для регистрации или login, пришлось бы добавлять в общий тип либо вводить несовместимое изменение RPC.
- **Не включать `ROLE_ADMIN` в общий enum.** Отклонено: административная identity является частью Auth domain, а разные wire-типы ролей создают преобразования и риск расхождения. Запрет self-register надёжнее задаётся валидацией операции, а не неполным enum.
- **Использовать `user_id` или JetStream delivery sequence вместо `event_id`.** Отклонено: один пользователь может порождать разные события, а delivery sequence описывает доставку, не логический факт. Оба варианта дают неверную границу дедупликации.
- **Передавать reset token или готовый URL в событии.** Отклонено: JetStream, consumer storage, tracing и DLQ расширили бы поверхность утечки одноразового секрета.
- **Передать владение reset request в Notification Service.** Отклонено: только Auth владеет credentials, identities и сессиями, поэтому раздельное владение нарушило бы атомарность смены пароля, потребления token и отзыва refresh families.

## Последствия

### Положительные

- Контракт каждого auth-сценария можно расширять добавочными полями без загрязнения `TokenPair`.
- Один enum представляет все роли identity, а публичная регистрация сохраняет явный запрет `ROLE_ADMIN`.
- Consumers получают стабильный ключ идемпотентности для at-least-once доставки `user.registered`.
- Reset token остаётся внутри границы Auth и не передаётся через асинхронную инфраструктуру.
- Смена пароля, одноразовость reset request и отзыв сессий контролируются одним владельцем данных.

### Отрицательные

- Клиенты должны обращаться к `response.tokens`, а не читать поля `TokenPair` непосредственно из ответа RPC.
- Наличие `ROLE_ADMIN` в `RegisterRequest` нельзя трактовать как разрешение self-register; серверная валидация и тесты обязательны.
- Поток доставки password reset требует защищённого синхронного вызова Notification → Auth и политики авторизации workload identity.
- Auth Service получает дополнительную таблицу, RPC, outbox event и обязанности по очистке истёкших reset requests.
- Переход от первоначальной формы T02 к wrapper responses несовместим на wire-уровне; он допустим только как формирование базовой `v1` до стабильной публикации. После фиксации `v1` аналогичное изменение потребует `v2`.
